# 管理画面と公開サイトを分け、公開サイトは前もって作った静的なファイルで配る

EmDash は入力の場所（管理画面と編集用の鍵のフォーム）にだけ使う。一般の人が見る公開サイトは、ビルドのときに EmDash の REST API から公開済みの中身を読んで HTML にし、静的なファイルとして配る。

理由は CPU の上限だ。Workers の無料プランでは、1回のアクセスに使える CPU が 10ms までで、有料プランにはしない。EmDash がアクセスのたびにトップページを組み立てると 70〜100ms かかった（`docs/notes/emdash-gates.md`）。参照をやめても 10ms は下回らない。静的なファイルは Worker を通らないので、上限にかからない。

同じ repo に `cms/`（EmDash、Worker `machibun-cms`）と `web/`（公開サイト、Worker `machibun2026`。年の名前を付け、URL は `machibun2026.yurumachi-yuruyuru.workers.dev`）を置く。公開・公開の取り消し・削除、公開中のものの保存があると、`cms/` のプラグインのフックが `web/` の Deploy Hook を呼び、公開サイトがビルドし直される。

## Considered Options

- EmDash のままアクセスのたびに組み立て、キャッシュで受ける: キャッシュに無いときは毎回上限を超えるので採らなかった。
- 中身の設計を変えて問い合わせを減らす（カテゴリを分類に、出演枠を出演者のくり返し項目に）: 年ごと・一つだけ選ぶ・本人と運営の編集を分ける、という中身の設計（`docs/content-model.md`）を崩すうえ、それでも 10ms は下回らないので採らなかった。
- Pages CMS など、中身を git に置く CMS: 連絡先や写真まで repo に入り、repo（いまは公開）を private にする必要が出るので採らなかった。
- microCMS など外部の CMS: 無料の枠（3人・5 API）に収まらない。編集用の鍵（ADR 0001）を外部サービスの上で作り直すことにもなるので採らなかった。
- Hono と D1 で自作する: 管理画面と認証を作って保守する手間が大きいので採らなかった。
- ビルドのときに D1 を直接読む: EmDash の表の作りに依存し、EmDash を上げるたびに壊れうるので、REST API を読むだけの token（`content:read`・`media:read`）で読む。

## Consequences

- 公開してから公開サイトに載るまで、ビルドの 1〜3 分かかる。
- 下書きを公開サイトの見た目で確かめる仕組み（EmDash の `?_preview=`）は使えない。最初は作らず、公開してから直すことが多いと分かったら考える。
- 写真はビルドのときに CMS から取って縮め、公開サイトの静的なファイルとして配る。写真を見るアクセスは `machibun-cms` を通らない。
- 公開サイトの Preview は CMS の Preview を、本番は CMS の本番を読む。token も環境ごとに分ける。
- 関門1（CPU）は、公開サイトではなく、管理画面と編集用の鍵のフォームが打ち切られないかで判断する。
